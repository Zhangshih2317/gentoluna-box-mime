## 1. 结果与适用范围

已经打通 PICO 经 USB 使用电脑网络、访问机器人 Apex 后端的链路，并补齐机器人向 PICO 主动发送的两路反馈。曾取得 VR 会话连接、机器人 Ready、模式切换后的实机关节反馈；执行过官方 Home，以及独立 SDK 的单腕低速往返测试。这些结果证实网络、反馈和运动控制的部分环节实际工作。

## 6. VR 是如何调用到机器人的

### 6.1 网络数据路径

```text
PICO Apex 应用
  | 头显姿态、手柄 / 身体追踪、遥操会话
  v
Android VPN / Gnirehtet（tun0: 10.0.0.2）
  | ADB reverse: localabstract:gnirehtet -> 电脑 tcp:31416
  v
Windows Gnirehtet -> 电脑有线 6.6.7.200 -> 域控 6.6.7.100
  | TCP 9010 会话；UDP 9000/9001 输入
  v
Apex / ROS 遥操处理 -> 运控 SDK -> 控制器 6.6.7.190

补充的反向反馈：
域控 6.6.7.100 -> UDP 9002/9003 -> 电脑 6.6.7.200
  -> 自定义 Node 中继 -> ADB forward tcp:39002
  -> 头显 PicoFeedbackRelay -> 头显本机 UDP 9002/9003
  -> PICO Apex 应用
```

USB 线在此承担 ADB 数据传输，电脑通过 Gnirehtet 提供网络。普通 USB 连接或给扩展坞供电，本身不等于 PICO 自动获得以太网。此次采用软件共享及反馈中继解决现有接线下的通信问题，没有把电脑网口直接变成头显的 USB 网卡。

### 6.2 自定义反馈中继

原 Gnirehtet 链路通过了头显主动访问测试，但机器人主动发送的 UDP 9002/9003 仍需补齐。此次新增：

- `R\tools\pico-feedback\relay.cjs`：绑定电脑 `6.6.7.200:9002/9003`，仅接受配置中的机器人源地址；通过 ADB 转发连接头显 TCP 39002。
- `R\tools\pico-feedback\PicoFeedbackRelay.java`：头显侧本机 TCP 服务，将帧转发到本机 UDP 9002/9003。
- `R\tools\pico-feedback\classes.dex`：上述 Java 程序的 Android 运行文件；由 ADB 推送到 `/data/local/tmp/luna-pico-feedback.dex`。
- 辅助进程使用 `app_process` 运行，不需要修改 PICO APK 或 root。

中继帧格式为大端 `uint16 目标端口 + uint16 数据长度 + 原始 UDP 负载`。端口只允许 9002/9003，负载长度有界；Node 侧处理拥塞时保留每端口最新待发送数据，启用 TCP_NODELAY，定时发送心跳。头显返回投递计数。

截至 11 月 5 日 15:22 停止时，`pico-feedback-state.json` 保存左右各 **383,089** 次接收、转发和头显 UDP 投递记录，`phase=stopped`。这验证辅助通道运行过，不证明端到端时延、姿态正确性或 PICO 应用逐帧消费。中继没有独立的机器人安全停止机制，也没有经过实时性认证；源 IP 白名单不是加密身份认证。

### 6.3 机器人内部控制路径

根据本地厂商对照包和实机接口反馈分析，主要链路为：

```text
VR_reader
 -> teleop_manager_v2
 -> control/teleop/ik_request
 -> ik_request_mux
 -> qp_controller
 -> joint_cmd_mux
 -> marvin_robot_node
 -> Gento SDK
 -> 控制器
```

本地对照配置为全身 22 自由度（双臂 14、身体 6、头部 2），QP 配置频率为 500 Hz，并存在 Home 启动门控、约 2 秒输出混合 / 切换过渡等配置。实机日志也出现等待 Home 后才输出的提示。**这些本地参数未通过 SSH 与实机逐项比对，不能作为已生效的限速保证。**

头显曾保存 `Fullbody_Pico_Controller` 模式及 175 cm 身高参数；身高未独立核实。用户报告已佩戴并校准腰腿追踪器，但这不等于已验证人体到机器人坐标映射、初始姿态偏差或使能瞬间目标连续性。

## 7. 接口兼容与控制语义

以下是历史验证结果，不是可直接照顺序执行的开机动作清单。

| 接口 / 功能 | 观察结果 | 开发注意 |
| --- | --- | --- |
| `GET /api/v1/modules`、模块 status/logs | 可查询服务和日志 | 服务 active 不代表机器人可安全运动 |
| `GET /api/v1/robot/status` | 可读 Ready、故障、模式和关节状态 | 同时检查反馈时效，不能只看 HTTP 200 |
| `/ws/v1/topics` | 可读取关节、VR 等主题 | 渲染模型成功不等于实机已连接 |
| `POST /api/v1/modules/{id}/start/stop/restart` | 已实际使用 | 启动 Robot/Tool 可能涉及设备初始化、使能 |
| `POST /api/v1/robot/ready` | 初始化成功过 | 不是运动安全验收 |
| `POST /api/v1/robot/mode`，请求 `mode=3` | 成功时双臂实机状态为 2；也出现响应成功但右臂状态 100 | 请求枚举与反馈枚举不能混用 |
| `POST /api/v1/robot/go_home` | 15:07 执行并返回成功 | 会产生真实全身运动；Home 不等于全零 |
| 降速 / `set_vel_ratio` 路径 | HTTP 503，服务不可用 | `speed_factor=1.0` 是缓存值，不能当硬件速度读回 |
| `/api/v1/control/set_input`、部分 IK / 底盘选择接口 | 当前组合返回 404 | 不根据按钮颜色推断配置已生效 |
| WebSocket 的 `teleop_motion_mode=arms_only` | 返回 `Unsupported teleop control message` | 未成功限制为仅双臂 |
| 旧后端 footkey 控制 | 对照代码存在对应处理 | 未验证其释放后停止语义；不应伪造按键作为恢复方式 |
| 底盘 `6.6.7.6:8080` | 网页可达 | 未发底盘运动命令、未做运动验收 |

早期将 `speed_factor=1.0` 理解为“必然全速”不准确，后已更正。现代参考代码中的 PD 倍率处理也不能直接套用本次旧版 JointImp 链路。实际速度应依据正在使用的控制模式、规划限值和新鲜反馈判断。

## 10. 全身快速扭转事件与开发缺口

### 已确认的事实

1. 模式启用与 Home 确实执行过，不能记为“只连接，未动作”。
2. `enable_luna_vr.py` 仅完成有限次数状态轮询；成功后让模式保持启用并结束，没有持续守护 VR、按键释放和网络丢失。
3. 之前 SDK 5% 的单腕动作不等于全身 VR 5% 限速；后端降速接口当时不可用。
4. “仅双臂”请求曾被后端拒绝，未验证已隔离身体运动。
5. 用户报告仅短按使能，松开后仍出现快速扭转；没有足够记录重建控制命令是否持续、排队或跳变。
6. 远程停止请求当时超时，同时读到有线链路断开；没有证据确定断线的起因和先后关系。
7. 网络恢复后停止并核实服务状态、关闭共享链路，用户随后手动恢复机器人。

### 不能确定的原因

待查方向包括追踪坐标系或标定偏差、初始目标与实机姿态差异、按键按下 / 释放语义、命令残留、模式切换过渡、规划器限速是否生效、反馈延迟及连接中断处理。现有记录不足以选择其中某一项作为根因，也不足以把责任归因于用户松键方式或网线操作。

### 应记录的开发责任

在完整验证全身速度限制、松键停止和初始姿态连续性之前就进入全身可运动状态，验证不足。仅凭健康状态轮询、现场空间确认和单腕测试继续推进全身遥操不够；这是联调流程需要纠正的问题。

后续工程验证需先建立同步记录与可独立验证的停止逻辑，在离线或隔离条件下核对映射、目标连续性和限速，再由熟悉该设备的现场人员依据厂商流程分阶段验收。不得把本交接中的历史脚本串接成无人值守启动流程。
