# 用户示教 HOME 与五组双臂动作

用户在 FXPlatform 中将两臂调整至期望姿态附近，并确认每轴与期望原点差值不超过 1°。
将反馈归到最近的 0°、+90°、-90°后，用户授权采用该原点执行五组双臂动作。
本文件与 `HOME.json` 为当前有效原点；早期模型候选已另行归档。

| 关节 | 左臂 ARM0（°） | 右臂 ARM1（°） |
| --- | ---: | ---: |
| J1 | 90 | -90 |
| J2 | -90 | -90 |
| J3 | -90 | 90 |
| J4 | -90 | -90 |
| J5 | 0 | 0 |
| J6 | 0 | 0 |
| J7 | 0 | 0 |

这是应用程序 HOME，不修改编码器零位、关节标定或厂家 HOME 参数。
该姿态来自用户现场示教；尚未测量法兰与实际地面的绝对夹角。

所有角度依次为 J1～J7，单位度；每轴偏离 HOME 不超过 3°。

每段先上传两臂轨迹，确认均处于就绪态，再用一次双臂掩码 `0x03` 启动。
两臂同时启动；路径长度不同，实际到达时刻可以不同，较早到达的一臂保持目标，
直到两臂轨迹均结束且反馈到位后才继续下一段。没有宣称硬件运动开始时刻的实测同步精度。

双臂速度和加速度倍率均设置并持续核对为 5%。厂家规划参数独立设为 0.01，
50 Hz 采样；逐点计算的规划峰值约 1.8°/秒。
本次检查包括完整轨迹限位、相邻目标变化、轨迹越界、实时反馈新鲜度、
身体/头部姿态变化、控制器错误和到位偏差；未进行完整碰撞模型认证。

## 程序

在工作区运行下列命令：

```powershell
# 离线显示目标，不连接机器人
python tools/dual_arm_five_moves.py

# 仅连接、读取和规划，不发送运动或倍率设置
python tools/run_dual_arm_remote.py --preflight

# 真实执行五组动作并返回 HOME
python tools/run_dual_arm_remote.py --execute
```

真实执行要求 FXPlatform 等其他客户端已断开，唯一 SDK 进程锁可取得，
双臂处于无错误 Position、无已有轨迹，起始每轴距离 HOME 不超过 1.1°。
预检通过后才设置 5% 并运行。默认不会清错、切模式或修改 BODY/HEAD。
任一段失败会停止双臂并结束，不自动继续，也不盲目执行回原点。

## 大幅版上传失败修复

用户自行启动后，`evidence/dual-arm-20261111-131021.jsonl` 记录首次上传
760 点返回 `-19: Format command failed`。尚未出现 `segment_start`，
未调用 RunTraj；StopTraj 双臂掩码 3 确认，随后释放 SDK。
这是原实现遗漏现场长轨迹上传兼容处理所致。

现场 `robot/hand/gento_arm_control.py` 已记录多包上传的格式化失败问题，并使用
250 点分段。修复采用相同的小段上传思路：每次不超过 250 点，
双臂按相同样本边界拆分，不抽点、不提高规划频率、不提高 5% 倍率。
中间小段附加终点保持并确认两臂到位，因此动作间存在短暂停稳，
预计整体约 2～3 分钟，不承诺连续无停顿运动。

只读复查显示双臂仍在 HOME、Position、错误码 0、倍率 5%；ARM0 留有状态 1
（上传已初始化但未完成）。SDK C++ 的 Config_SetTraj 明确允许此状态重新初始化，
仅在轨迹状态 >=3 时拒绝上传。程序只允许首段在静止且 HOME 附近时替换状态 1，
仍拒绝覆盖状态 2 的已就绪轨迹及任何正在运行的轨迹；没有自动切换模式或清错。

修复后 9 项离线测试通过；只读厂家规划预检通过，
见 `evidence/dual-arm-20261111-131351.jsonl`，上传分段点数为 174～241 点。
尚未替用户进行修复后的真实上传/运动验收。仍运行工作区根目录
`run_dual_arm_large.py`，只读预检通过后输入 RUN 才上传并执行。

## 上传超时及状态 2 恢复修复

后续用户执行日志 `evidence/dual-arm-20261111-131546.jsonl` 显示：
ARM0 上传 240 点返回 `-10`（Operation timeout），随后控制器轨迹状态成为 2。
SDK C++ 的初始化与上传确认等待各约 10 毫秒，因此函数超时不等于上传未完成。
这次同样没有发送 RunTraj。此前直接将所有非零返回值作为失败的处理不完整。

现已对 -10 增加最多 0.5 秒状态回读：从 0/1 变成 2 时认定本次上传就绪，
不重复上传；如果调用前已经是 2，必须得到本次新上传的确认，不能把旧状态 2
误当成功。模糊结果至多重新初始化上传三次，全程不发送启动指令；
仍未确认或有运行状态/控制器错误则终止。其他错误码不自动重试。

只读预检允许报告静止、HOME 附近的状态 1/2；用户在入口输入 RUN 时，
明确授权替换未启动的残留数据。执行入口传入 `--replace-pending`，
首小段先重新上传双臂新数据、确认就绪，再发送一次双臂启动。
没有该参数的真实执行仍拒绝覆盖已有状态 2；后续小段也不允许覆盖残留状态。

13 项离线测试通过。已完成真实“只上传原位点、不启动”验证：
双臂分别上传 250 个当前位姿样本成功，再分别上传 5 个当前位姿样本成功，
没有调用 RunTraj。当前控制器留下的是这 5 个原位保持样本（状态 2），
SDK 已断开，双臂仍为 HOME、Position、错误码 0、5% 倍率。
证据：`evidence/dual-arm-20261111-131923.jsonl`。
同一 Windows 用户入口的只读预检随后通过：
`evidence/dual-arm-20261111-131941.jsonl`。
尚未代替用户执行修复后的五组大幅运动。

## 大幅动作完成与连贯版

用户自行运行完成，并明确反馈“动作无干涉”，要求连接动作、不再出现停顿。
成功证据为 `evidence/dual-arm-20261111-132115.jsonl`：
五组目标及返回 HOME 均完成，最后双臂 Position、错误码 0、倍率 5%，SDK 已释放。

根目录 `run_dual_arm_large.py` 现在默认传入 `--large-wrist --continuous`。
沿用同样的 HOME、目标、厂家规划速度及加速度；去掉每段一秒保持，
拼接时仅去除重复边界点，末尾 HOME 保留一秒保持。全程只调用一次
`runtime_run_traj(3)`，不再拆成 28 次小段启动，不在途经目标处等待反馈。
方向反转时仍按厂家规划减速到零并反向，不承诺换向时速度不变。

长轨迹上传采用厂家 SDK 已导出的 L0 接口：
`FX_L0_Arm0/1_Runtime_InitTraj(0, count)` 初始化完整缓冲区；
确认轨迹状态 1 后，用 `FX_L0_Arm0/1_Runtime_SetTraj(0, serial, count, data)`
按顺序每包最多 50 点上传，包间留 20 毫秒排空发送缓冲区。
该等待全部发生在运动启动之前。两臂新缓冲区均确认状态 2，
且实际位置未离开轨迹起点时，才发送一次双臂启动。
上传失败、反馈过期或运动异常时停止并退出，不退回分段运动或自动重试启动。

接口依据为机器人本机 SDK：

- `C_SDK/L0Control/L0Robot.h` 的 InitTraj / SetTraj 声明。
- `C_SDK/L0Control/RobotCtrl.cpp` 的 InitTraj 限制 5～5000 点、
  SetTraj 单包 1～50 点，以及 SetRawData 写入 RuntimeACB 的实现。
- `C_SDK/L1Robot/L1Robot.cpp` 的 Config_SetTraj 原实现：
  同样初始化及上传缓冲区，但连续入队全部数据包，并仅短暂等待就绪。

验证结果：

- 19 项离线测试通过，包括完整路径保序拼接、容量拒绝、旧状态 2 不可当新确认、
  双臂上传后单次启动、上传失败停止、原位上传不启动、HOME 起终点相同不能误报完成。
- `evidence/dual-arm-20261111-133015.jsonl`：只读厂家规划预检通过，
  4861 点，名义时长 97.22 秒，规划关节峰值约 1.8°/s，中途附加保持点为 0。
- `evidence/dual-arm-20261111-133029.jsonl`：双臂分别成功上传 5000 个当前位置保持点，
  每臂 100 包；随后各上传 5 个原位保持点替换。未发送 RunTraj，
  最终双臂仍为 HOME、Position、错误码 0、5% 倍率，SDK 已断开。


速度和加速度参数独立传递到 SSH 运行端，范围为有限数值 1～100。
