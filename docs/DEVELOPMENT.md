# 开发大纲与阶段成果

范围：2026-11-11 至 2026-11-13，本工作目录内留存的实现、点位、现场日志和分析。
这是根据现存资料整理的开发记录，不是完整聊天逐字稿，也不是所有历史源码版本的 Git 时间线。
最初仓库没有提交；公开仓库的首个提交是整理后的基线，不能据此还原每次修改。

## 一、目标与需求变化

1. 初始任务为空手模拟搬箱，无箱子、无夹爪：下蹲、合抱、站起、转腰45°、站立张臂、自动回 HOME。
2. 初始尝试用关节角幅度描述下蹲，实际出现整体倾斜。用户接管手动示教并多次记录。
3. 按示教姿态建立 B2/B3/B4 配合关系，完成“站起10cm”、回 HOME 和负向45°转腰。
4. 从分步流程改连续流式，随后增加速度，暴露软件到位、回显、跟随和调度阈值问题。
5. 加装双指夹爪后，用户报告软件急停触发掉力；记录中急停请求与保持行为成为单独问题。
6. 用户明确允许各轴2°偏差，要求一秒内两次合格反馈即可继续，保留其他故障检查。
7. 将下蹲改为物理下降30cm；分析高速下的 BODY 摆动与不同轴跟随。
8. 双臂采用厂家 Position 整点下发，BODY 保留协调轨迹；分别设置速度和加速度。
9. 单轮多次成功后，复制独立六轮版本，在原有负向45°基础上加入正向45°，交替完成整个动作。
10. 整理公开项目：配置化部署、保留证据、日志脱敏、明确依赖与许可。

## 二、2026-11-11：接入、HOME、示教与首个完整流程

### 控制接入

核对 ROS 网关与厂家 SDK 的控制权。独立 SDK 与 FXPlatform/网关不能同时持有连接；
出现 Link -22 时先处理连接归属，不能把它解释成角度或电机问题。
直接 Windows SDK 路径不成功后，采用 Windows SSH 调度机器人端 Python SDK。
操作者连接心跳、进程身份标识和反馈记录用于跟踪运行。

### HOME 与初期双臂测试

用户确认的双臂 HOME：

```text
ARM0 [ 90,-90,-90,-90,0,0,0]
ARM1 [-90,-90, 90,-90,0,0,0]
BODY [-0.744,9.281,-17.364,5.456,-0.296,-1.653]
```

这些是示教动作原点，不是编码器零位。头部保持当时反馈，不能忽略缓存对头姿的绑定。
早期双臂五组动作、小幅及较大幅度验证作为接入成果归档。

### BODY 异常与人工示教

旧 `run_box_motion.py` 执行中 BODY 出现非预期运动，B1/B5/B6 也有变化。
不能简单归咎于某一蹲姿角比例；旧 BODY 缓冲执行路线停用。
独立恢复到保存起点，随后用户在 FXPlatform 手动示教。
UI 读数与后来 SDK 多帧读数分别标注，避免把截图读数描述成实时 SDK 验证。

记录了两轴浅蹲、B3/B4 配合、深蹲、站姿及转腰点。
示教建立的共同关系是保持 B2+B3+B4 的目标角度和，并沿既有分支变化。
原先“30°角幅”与后来“30cm躯干下降”是两个不同需求。

### 运动学与第一版搬箱

使用与设备对应的 BODY/HEAD 运动学，求解100mm站起。
随后构建八阶段完整流程。早期成功日志：
`box-mime-taught-20261111-160754.jsonl`。
这个成功属于当时低速分步实现，不代表后续每个加速版本均已验证。

## 三、2026-11-12：停止行为和恢复入口

夹爪安装后出现 `Torso pitch compensation mismatch`，外层异常路径请求急停，
并记录 `stop_unconfirmed`；用户报告掉力。日志不证明供电、电机制动或机械抱闸的真实状态。

必须区分四种行为：

- 正常到位后继续下一阶段；
- 普通跟随偏差或晚到：保持/等待；
- 正常结束：保留 Position；
- 控制器故障、反馈失效等硬故障：仍有急停处理。

开发中多次因启动参考过于固定而拒绝回 HOME。
恢复入口改为结合当前读数和既有恢复分支检查，不能只重用旧失败前的姿态。
独立 HOME 与搬箱主流程分开，避免“只想回原点却继续搬箱”。

## 四、2026-11-13：30cm、协调调速和实机闭环

### 下蹲与 BODY 时间规划

深度由运动学求解，不将“30cm”直接写成某个关节30°。
B2/B3/B4 使用共同进度，速度、加速度、jerk 共同约束持续时间。
BODY 在30/40/80%测试中呈现不同跟随误差，B3的表观滞后较大。
现有记录支持动态跟随差异，但不支持发布固定的“B3提前0.12秒”补偿表。

已实现的是**几何协调与时间参数化、等待后重规划**，不是已辨识的负载动态补偿。
SDK 的 BODY 运行时比例是组级标量，不是每轴独立比例。

### 双臂“100%却很慢”

核对调用与 SG 反馈后发现倍率确已到100%，但软件外部轨迹另外限制了
18°/s、9°/s²、9°/s³以及最短时长，短动作主要由 jerk 限制。
因此用户目测缓慢的原因不能靠再次设置100%解决。

双臂四个正式动作改为原生 Position 完整目标；每臂每阶段下发一次，
由内部控制器规划，到位后再进入下一步。BODY仍采用原共同进度轨迹。
同时更新原生路径采样与监控，防止套用旧流式的静止轴/指令增量阈值。

### 全身2°与反馈时间

ARM0、ARM1、BODY 和 HEAD 保持位统一按默认搬箱的2°目标容差；
到位需要两次不同反馈帧，相隔0.1～1秒。
完整终点各轴已合格时，不再因若干轴误差相加而否定到位。
SDK命令回显检查独立存在，不能把输入目标、内部规划目标和实际位置混用。

逐周期日志包含读取时间、帧号、发送目标、实际位置、阶段与等待状态；
异常判定前记录触发反馈，避免发生错误却没有对应帧。
短时调度间隔超限冻结进度而不追赶时间；超出硬限仍可能失败。

### 已完成结果

- 最近三次单轮各8阶段成功，最大 HOME 误差分别0.001°、0.002°、0.001°。
- 最新单轮双臂和 BODY 均100%速度、50%加速度。
- 六轮使用独立代码快照和双方向缓存，48阶段成功，8404条反馈无丢弃，
  各轮 HOME 最大误差不超过0.002°。
- 正常结束保留 Position；这些日志没有出现软件急停请求。

具体文件与指标以 [VALIDATION.md](VALIDATION.md) 和机器可读索引为准。

## 五、交付与仍未解决的边界

已交付可读、可配置的两套主流程和独立 HOME；公开副本移除个人连接脚本依赖。
所有现场参数仍是特定机器的样例。未声称解决：

- 任意未知姿态下的自动恢复；
- 夹爪/箱子/外部环境的完整碰撞建模；
- 全身任意2°扰动的连续无碰撞证明；
- 未配置负载、无抱闸轴的通用带载故障停止；
- 各BODY轴的动力学辨识与固定延迟前馈补偿；
- 不同固件、SDK、机械结构上的即装即用。

这些边界不影响查阅和复用已经实现的编排、反馈和分析模块，但应在移植时显式处理。
